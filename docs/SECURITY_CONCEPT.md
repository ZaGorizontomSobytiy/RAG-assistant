# Концепция безопасного RAG-ассистента

Краткое описание ролей, мер защиты и предобработки данных (в т.ч. маскировка персональных данных до отправки в LLM).

---

## 1. Роли и доступ к данным

| Роль | Просмотр | Изменение | Ограничения |
|------|----------|-----------|-------------|
| **Администратор** | Все документы, ответы бота, логи, метаданные индекса | Загрузка/удаление документов, настройка доступа, очистка кеша, конфиг | Доступ по сильной аутентификации (2FA) |
| **Аналитик** | Документы и ответы только из разрешённых коллекций/папок | Добавление документов в «свои» коллекции; без удаления чужих | Фильтр по метаданным (например, `department=analytics`); нет доступа к персональным и финансовым данным |
| **Гость** | Только публичные документы (FAQ, общие инструкции) | Ничего | Фильтр по источнику; лимит запросов; без кеша и логов |

---

## 2. Меры защиты данных

| Мера | Назначение |
|------|------------|
| Разделение по коллекциям/метаданным | В ChromaDB — отдельные коллекции или метаданные (`role`, `department`, `is_public`). При запросе подставлять фильтр `where` по роли. |
| **Предобработка: маскировка ПД до LLM** | См. раздел 3 ниже. |
| Постобработка ответов | Перед выдачей пользователю — замена упоминаний ПД (ФИО, телефоны, счета) на «[скрыто]» или проверка по политике. |
| Проверка контекста перед LLM | Не передавать в LLM чанки с меткой «конфиденциально», если у пользователя нет прав. |
| Логирование и аудит | Кто (роль/ID), какой запрос, по каким документам, выдан ли ответ или заблокирован. |
| Ограничение утечки через промпт | В системный промпт: «Отвечай только на основе контекста; не выводи цитаты из внутренних документов для гостя». Порог релевантности. |
| Изоляция кеша по ролям | Кеш ключить по (роль, запрос). Ответ аналитика не отдавать гостю. |

---

## 3. Предобработка: маскировка персональных данных до отправки в LLM

Чтобы персональные данные не попадали к внешнему провайдеру (OpenAI, GigaChat и т.д.) и не терялось качество RAG, применяют **предобработку** текста перед индексацией и/или перед формированием контекста для LLM. Два основных варианта:

### 3.1. Детерминированные псевдонимы

- **Идея:** каждое уникальное значение ПД (ФИО, телефон, email, номер счёта) заменяется на один и тот же псевдоним во всём корпусе.
- **Примеры:** «Иванов И.И.» → `[ЛИЦО_1]`, «+7 999 123-45-67» → `[ТЕЛ_1]`. Один и тот же человек/номер всегда даёт один и тот же токен.
- **Плюсы:** модель может рассуждать («документ подписан [ЛИЦО_1]»), контекст сохраняется; в ответе для ролей с доступом можно подставить обратно реальное значение по справочнику `[ЛИЦО_1] → Иванов И.И.`.
- **Реализация:** при загрузке документа — NER/регулярки для выделения ПД, хеш или ID в справочнике, замена на `[ТИП_ID]`; справочник хранится только у себя, в LLM уходят только псевдонимы.

### 3.2. Ролевые метки

- **Идея:** персональные данные заменяются не на уникальный ID, а на роль/тип участника.
- **Примеры:** «Иванов И.И.» → «директор», «Петрова А.С.» → «заявитель», «клиент»; телефоны/email → «контакт заявителя», «контакт директора».
- **Плюсы:** модель отвечает в терминах ролей («документ подписан директором»); минимальный объём обратимых данных.
- **Минусы:** теряется различие между несколькими людьми одной роли; подходит там, где важна именно роль, а не личность.

### 3.3. Совместное использование

В реальных проектах часто комбинируют:

- **Детерминированные псевдонимы** — для связности ответов и возможности раскрыть ПД авторизованным ролям (админ, аналитик своего отдела).
- **Ролевые метки** — для гостя или для документов, где важна только роль (например, «заявитель», «исполнитель»).

Настройка в конфиге (например, в `config.yaml`) может задавать режим по умолчанию и по роли: для гостя — только ролевые метки, для аналитика — детерминированные псевдонимы с возможностью раскрытия при выводе.

## 4. Схема потока

Сначала определяем, кто обращается (аутентификация и роль), затем обрабатываем запрос с учётом этой роли.

```
[Аутентификация и определение роли] → [Запрос (вопрос пользователя)]
    → [Фильтр документов по роли (where)]
    → [Предобработка контекста: маскировка ПД (детерминированная / ролевая)]
    → [RAG: поиск → контекст только из разрешённых чанков]
    → [LLM получает уже замаскированный контекст]
    → [Постобработка ответа: маскировка при необходимости]
    → [Для разрешённых ролей: подстановка ПД из справочника по псевдонимам]
    → [Лог] → [Ответ пользователю]
```

## 5. Применение в реальных проектах

- **Корпоративный портал:** администратор управляет документами и правами; аналитики — только свои отделы; гости — публичная база. Разделение по коллекциям/метаданным и фильтр по роли — основа. Предобработка с детерминированными псевдонимами позволяет не отправлять ПД во внешнюю LLM и при этом сохранять связность ответов; для гостя можно использовать только ролевые метки.

- **Медицина / персональные данные:** доступ к историям — только авторизованные роли; в контекст для LLM попадают только обезличенные или псевдонимизированные фрагменты. Детерминированные псевдонимы дают возможность «узнать» одного пациента по всем документам без передачи ФИО в API; ролевые метки («пациент», «врач») — для обобщённых ответов без раскрытия личностей.

- **Финансы:** отчёты и премиальные данные — только для аналитиков/руководителей; предобработка (маскировка счетов, ФИО) до отправки в LLM обязательна при использовании внешнего провайдера. Аудит логов и изоляция кеша по ролям дополняют защиту.
